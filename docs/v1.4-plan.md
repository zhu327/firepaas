# firepaas v1.4 计划：节点本地状态完整性、缓存预热与可运维性

> 状态：方向性规划草案 v1（2026-08-31）。前置版本为 v1.3。
> 本版本只从 v2 计划中提取能够复用现有控制面、agent 和 node-local 数据模型的
> 增量，不引入 durable artifact plane、build service、portable memory template
> 或 multi-cluster global plane。

## 1. 版本定位

v1.4 不改变 v1.x 的状态权威和数据路径，目标是在不承诺跨节点 durability 的前提下，
补齐节点本地 snapshot、volume、dataset 和 OCI image cache 的完整性、可观测性与
运维能力：

1. 先关闭 v1.2/v1.3 已有实现中的状态机、能力广告和发布证据缺口；
2. 为 node-local snapshot/volume 建立 inventory reconciliation、完整性检查和
   fail-closed GC；
3. 把已有 OCI image 自动预取扩展为显式 prewarm、覆盖率查询和有界 cache pin；
4. 完成 DATASET_RO 导入、只读多挂载和 crash cleanup；per-execution CoW 仅在能力和
   真机验收成立后启用；
5. 增加 restore preflight 和性能证据，为未来 v2 portable artifact/template 决策提供
   数据，但不提前冻结 v2 的 durable manifest 或跨节点格式。

建议拆成 **v1.4.0 baseline hardening、v1.4.1 local integrity、v1.4.2 image
prewarm、v1.4.3 dataset/restore usability**。2 人约 6～10 周；若入口门禁尚未完成，
门禁修复时间不计入功能排期。

## 2. 设计约束

- PostgreSQL 继续保存业务事实；agent 继续保存 node-local artifact 的 observed state；
  Redis 只保存可重建投影和短期结果。
- snapshot、LOCAL_RW volume、DATASET_RO materialization 仍明确标记
  `locality=node-local`、`durability=best-effort` 和 `origin_node_id`。
- 不增加统一 artifact manifest/chunk/replica 数据模型，不把 S3/MinIO 提升为 snapshot
  或 volume 的 durable content 权威。
- 不改变 `client → edge → agent proxy → workload` 流量路径。
- 所有新增能力通过 capability 或 feature flag 启用；按 ADR-0036，local GC 配置为
  `FIREPAAS_LOCAL_GC_MODE=off|dry-run|delete` 且默认 **`off`**；旧 agent 不支持时必须
  显式降级或拒绝，不能猜测成功。
- 只新增顺序 migration；不重写 v1.2/v1.3 已有 migration。

## 3. 入口门禁

- 当前 v1.2/v1.3 工作树整理成可复现基线，`make check` 通过且生成代码无漂移；
- ADR-0028～0030 转为“已接受”，当前 snapshot/volume/dataset 实现与其一致；
- hypeman 依赖固定到经审查的不可变版本，或明确记录本地 replace 仍阻塞发布；
- v1.3 snapshot/volume/dataset 的目标 package tests 和单节点 e2e 可重复执行；
- 至少完成一次双 compute 节点的 capability、leader handover 和 node loss 演练；
- 节点磁盘 high/low watermark、snapshot/dataset checksum 成本已有基准；
- B 的 inventory/integrity/删除协议、C 的 prewarm/pin 治理分别形成已接受的 ADR 或
  设计记录；任何 destructive GC 在协议审查和恢复演练前不得启用。

## 5. V1.4-A：Baseline Hardening

本工作包不增加产品语义，先使当前 v1.3 能力与其声明一致。

### 必须修复

- snapshot delete 对已经进入 `DELETING` 的操作幂等收敛，不能在 controller 重试时
  因 `DELETING → DELETING` 冲突而失败；
- snapshot fork/restore 的引用保护与实际 consumer/operation 生命周期一致，删除不能
  只避开 RPC 窗口；
- volume `UNAVAILABLE → READY` 必须依据 agent inventory，而不是仅依据 node
  heartbeat；inventory 无法确认时保持 `UNAVAILABLE`；
- capability 广告必须由实际装配和验收推导；未交付的 dataset overlay 不得发布
  `volume.dataset_overlay.v1`；
- snapshot、volume、dataset controller/store 增加状态机和并发回归测试；
- DATASET_RO v1.4 只接受无 userinfo/query/fragment 的 credential-free HTTPS URL；URL
  不得进入日志、事件或错误正文。需要认证的对象源和平台签发预签 URL 留待独立 ADR，
  在此之前不持久化或代理来源凭证；
- 文档和 API 必须继续暴露 node-local、best-effort 和 origin node，不得暗示节点丢失后
  可恢复。

### 验收

- create/delete/retry、leader handover 和 agent 暂时不可达组合场景可收敛；
- fork/restore/retention/delete 并发不产生 use-after-delete；
- node 恢复但本地产物不存在时不会错误恢复 READY；
- capability API 与 agent 实际可执行行为一致；
- operation trace、日志和 PG 行中没有预签 URL credential。

## 6. V1.4-B：Node-local Inventory、Integrity 与 GC

### 目标

在保持 node-local 语义的前提下，提前吸收 v2 content plane 中“校验、引用和 GC”的
方法，但不引入跨节点复制和统一 durable artifact 模型。

### 能力

- agent 定期上报 snapshot 和 volume inventory：本地 ID、类型、大小、可用的 checksum
  或 digest、sealed/attached 状态、完整列表 generation 和观测时间；
- controller 分别对账 PG snapshot/volume 与 origin-node inventory；不建立跨类型统一
  artifact 表；旧 agent 或不完整列表只能产生 `UNKNOWN`，不能推导 `MISSING`；
- integrity 按资源类型定义：不可变 snapshot 和 sealed `DATASET_RO` 可使用内容 checksum；
  attached `LOCAL_RW` 只报告 materialization/device/filesystem metadata health，不计算或
  比较内容 digest；如需内容 scrub，只允许 detached/quiesced volume，并在重新 attach/
  写入后使该 observation 失效；
- 为资源增加正交的 integrity observation，例如
  `UNKNOWN|METADATA_VERIFIED|CONTENT_VERIFIED|MISSING|CORRUPT`，不复用业务生命周期
  状态表达校验结果；
- 创建完成后按类型校验必要事实再进入 READY；周期 scrub 仅在节点 IO 预算允许时执行；
  若上游不能重新计算 checksum，只能标记 `METADATA_VERIFIED`；
- 本地 orphan、cache 和临时 spool 扫描；roots 至少包含 PG 资源、active attachment、
  snapshot reference 和 in-flight operation；
- 第一阶段 GC 只自动处理可重新拉取的 image cache、已过期 spool 和明确的失败操作临时
  文件。snapshot、LOCAL_RW 和无可靠来源的 DATASET_RO 只报告，不自动删除；
- 删除协议为 PG 原子 tombstone/claim 阻止新引用，agent 在删除临界区再次检查本地
  attachment、in-flight ledger 和 generation，再先 rename 到 quarantine；宽限期后仅对
  可重建内容物理删除。任何检查失败均中止；
- GC 使用 high/low watermark、最小年龄，默认 `dry-run`；
- 暴露 inventory drift、scrub failure、orphan bytes、GC candidate/quarantined/deleted
  bytes、checksum latency 指标和租户可见事件摘要。

### 一致性与安全

- node heartbeat 只能影响 availability，不能证明 artifact 存在；
- `MISSING/CORRUPT` 不允许 restore/attach；不得自动创建空同名 volume；
- create/compress/import 未完成的临时文件不能成为可 attach 的 READY 资源；
- delete 前必须持有 PG claim 并由 agent 原子重查本地引用；任何一侧查询失败均停止该
  节点删除；
- LOST 仍只允许由节点退役、人工确认或权威 inventory 证据触发；
- quarantine 回滚只适用于宽限期内尚未物理删除的内容；node-local snapshot、LOCAL_RW
  和无可靠来源的 dataset 不存在自动恢复路径，因此不得进入自动物理删除候选。

### 验收

- 删除本地文件、篡改 chunk/文件、agent crash、leader handover 后状态正确收敛；
- create/delete/attach/fork/restore 与 GC 并发不删除在用内容；
- dry-run 输出与真实 roots 一致；delete 模式只靠可重建 cache/spool 降低水位，无法达到
  low watermark 时告警并停止，不扩大到不可恢复资源；
- scrub 受并发和 IO 配额限制，不使应用启动和尾延迟超预算；
- 所有 inventory 和事件按 project 隔离，不包含本地路径或 credential。

## 7. V1.4-C：OCI Image Prewarm、Coverage 与 Cache Pin

### 目标

扩展已有 rollout top-K `PullImage` 和 image affinity，不创建新的镜像仓库或 artifact
存储，使操作者可以在发布前确认目标 node pool 的镜像缓存情况。

### 能力

- 显式 prewarm API/CLI：按 image digest、node pool 或明确节点集合派发已有
  `PullImage`；
- prewarm operation 持久化于 PG，重试幂等；leader 切换可恢复，不重复产生业务结果；
- coverage 查询返回 eligible 节点数、cached/pending/failed 数和每节点最近观测时间；
- 可选短期 cache pin：主键/作用域包含 `project_id + image_digest + target selector`，
  记录 owner、reason、expires_at；GC 按节点计算 roots，不能让一个 pin 隐式保护全集群；
- 按 ADR-0037，在 project→node-pool ACL 有独立 ADR 与数据模型前，prewarm、coverage、
  pin/list/unpin 全部只允许 root/admin；project ID 仍用于配额和审计。后续 ACL 落地后才
  校验 project scope 和 node-pool 权限；同时限制目标节点数、最大 TTL、每项目 pinned
  bytes 和 prewarm 并发；
- pin 和磁盘 hard watermark 冲突时拒绝新的 pin/prefetch，不能突破节点准入；
- coverage 只统计调用者有权操作且满足部署硬约束的 eligible 节点；
- rollout 自动预取继续是 best-effort；显式 prewarm 可以等待目标覆盖率，但不自动创建
  deployment。

### 非目标

- 不复制 registry，不改变 OCI digest 权威；
- 不保证所有节点永久缓存；
- 不引入 filesystem/memory template；
- 不用 Redis 作为 pin 或 completion 的业务权威。

### 验收

- 重复 prewarm 不重复下载已缓存 digest；
- leader/agent 重启后 operation 可收敛；
- pin 生效期间 GC 不删除对应 digest，过期后可按现有策略回收；
- 节点不健康、能力不足、磁盘水位超限时给出明确逐节点结果；
- prewarm 压测不影响已有 workload 的启动和磁盘 SLO。

## 8. V1.4-D：DATASET_RO 与 Restore Usability

### DATASET_RO 完成

- 导入仍由 agent 直连来源，主 API 不缓冲大文件；
- v1.4 仅支持 credential-free、digest-pinned HTTPS 来源；持久 operation 保存规范化 URL、
  digest 和大小/文件数限制，但日志、事件和错误正文只记录 URL 摘要；带认证的对象来源、
  opaque source ID 和派发时签名属于后续独立 ADR；
- 保留 compressed size、expanded size、file count、archive traversal、symlink、
  hardlink、device/FIFO 和 decompression bomb 防护；
- agent 启动时清理过期 spool，并用 operation/volume ID 避免误删在途导入；
- 完成同节点多 machine 只读挂载和删除引用保护；
- per-execution CoW 只有在 hypeman capability、disk admission、cleanup 和真机 e2e
  全部通过后才启用；否则 API 明确拒绝且不广告 capability。

### Restore Preflight

新增只读 preflight，不改变实际 restore/fork 状态机：

- 返回 snapshot locality、integrity、origin node availability、compatibility 是否匹配、
  可用 restore mode 和缺失 capability；
- `memory` 不兼容时明确拒绝；`auto` 只报告是否可降级到 filesystem，不执行隐式操作；
- 记录 cold boot、filesystem restore、memory restore 的 p50/p95、数据大小和节点能力，
  为 v2 memory template/UFFD 是否立项提供证据；
- compatibility 的结构化字段只作为可观测信息；旧 opaque compatibility key 仍保留，
  不在 v1.4 承诺跨节点可移植格式。

### 验收

- 带 userinfo/query/fragment 的来源 URL 被拒绝，URL 原文不进入日志、事件或错误响应；
- agent crash 后没有无限期 spool，重试不会发布半成品 dataset；
- DATASET_RO 多挂载互不影响，base digest 不变；
- overlay 未启用时 fail closed；启用时写入互不可见，machine 删除后 overlay 被回收；
- preflight 与实际 restore 的兼容性结论一致；节点变化后旧 preflight 不能当作执行授权。

## 9. 发布切片和依赖

```text
v1.3 implementation baseline
        ↓
v1.4.0 baseline hardening
        ├────────────→ v1.4.1 local inventory / integrity / dry-run GC
        ├────────────→ v1.4.2 image prewarm / coverage / pin
        └→ v1.4.3 dataset hardening / restore preflight

v1.4.1 inventory semantics ─→ local GC delete mode
hypeman + e2e evidence ─────→ optional dataset CoW
performance evidence ───────→ future v2 memory template / UFFD decision
```

A 必须先完成。B、C 在各自设计记录被接受后可并行；D 依赖 A，若引入本地 artifact
GC，则删除路径还依赖 B 的 inventory/roots 语义。任何 protobuf 变更必须先定义
完整列表标志、observation generation/time、旧 agent 缺字段语义和对应 feature ID，
再串行生成和合并两端代码。

## 11. 全局非目标

- S3/MinIO durable artifact manifest、chunking、resumable upload 和 replica controller；
- snapshot、volume、dataset 的跨节点自动 materialization 或 durability SLA；
- source/Dockerfile build、BuildKit worker、SBOM/provenance 生成；
- filesystem/memory template lineage、portable memory snapshot、P2P、UFFD；
- multi-cluster/global plane、active epoch、global DNS failover；
- balloon、GPU、多 hypervisor 节点池；
- 跨集群 RW block volume、在线 VM 迁移、overlay/6PN/service mesh。

## 12. 与 v2 的关系

v1.4 只提前验证 v2 中不改变权威边界的部分：

| v2 方向 | v1.4 提前做 | v1.4 明确不做 |
|---|---|---|
| Artifact plane | checksum/inventory/reference/本地 GC/指标 | durable manifest、chunk、replica、跨节点恢复 |
| Build service | 无 | queue、builder、BuildKit、源码上传 |
| Template/snapshot | compatibility preflight、OCI prewarm、本地 CoW（条件） | portable snapshot、memory template、lineage DAG |
| Multi-cluster | 无；只继续单集群 HA/DR 证据 | global plane、epoch、跨 cell failover |
| Balloon/UFFD/GPU | 只收集性能和容量证据 | 运行时能力本身 |

v1.4 的数据模型不应假设未来 v2 manifest/chunk 格式。未来进入 v2.0 时，通过新增
versioned adapter 将 node-local snapshot/volume 导入 durable content plane，而不是让
v1.4 的本地 inventory 表承担全局 artifact authority。

## 13. 风险、发布与回滚

| 风险 | 控制与回滚 |
|---|---|
| inventory 误判导致数据丢失 | availability 与 integrity 分离；查询失败 fail closed；GC 默认 dry-run |
| scrub 影响节点 IO | 并发/带宽预算、低优先级、按节点关闭；超 SLO 立即停 scrub |
| cache pin 占满磁盘 | pin TTL、hard watermark、项目配额；回滚时停止新 pin 并保留既有 expiry |
| dataset 来源泄漏 | v1.4 仅允许 credential-free URL；日志/事件只记录摘要；认证来源等待独立 ADR |
| CoW capability 虚假广告 | capability 由真实装配和 e2e 推导；证据不足保持关闭 |
| migration 回滚困难 | 只新增 nullable/有默认值字段和新表；回滚二进制时保留数据，不做 down migration |

发布顺序为 API/controller 先兼容新字段但保持 `FIREPAAS_LOCAL_GC_MODE=off`，随后滚动
agent，确认 capability、inventory epoch/generation 与 observation age 后再打开 read-only
observation。当前 pinned hypeman 没有 lock-aware quarantine/scrub API，physical delete
不可启用；未来能力、协议测试和单节点 rollback 演练全部完成后，才可按节点审批 `delete`
或 dataset CoW。回滚前先停止受理新 operation，取消或终结新 operation kind，
等待队列在有界时间内清空，并将 quarantine 内容恢复原位；确认旧二进制能忽略新增 nullable/
有默认值字段后再回滚。已经物理删除的 node-local 数据不能靠二进制回滚恢复，因此不可恢复
资源不进入自动删除。不删除新增表列，不改写历史 migration。
