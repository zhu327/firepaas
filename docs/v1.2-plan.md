# firepaas v1.2 计划：安全运行时与资源治理

> 状态：规划草案 v1（2026-08-28）。本计划综合 firepaas v1.1、E2B infra 与
> hypeman 的能力对照。v1.2 不改变 Nomad、状态权威和 L3 edge-routed 网络等既有
> 架构原则；关键决策见 ADR-0023～0026。

## 1. 版本定位

v1.2 的目标是把 firepaas 从“可部署和路由无状态 VM”提升为“可安全操作、可等待、
可治理的内部 PaaS”：

1. 关闭 `unsafe-persisted-env` 所代表的 secret 明文落盘缺口；
2. 正式交付 logs/exec/cp，而不是只保留 proto 占位；
3. 用 capability discovery 支持 agent/hypeman 混合版本和能力驱动调度；
4. 完成 TTL、restart policy 与 Wait API 的控制面闭环；
5. 把磁盘纳入配额、预约和硬准入，并补齐 API 动态限流；
6. 提供项目级生命周期事件、基础使用指标和引用感知缓存 GC。

排期基线：**2 人 13～17 周；1 人 20～26 周**。该工期不包含 v1.1 的 72h
标准拓扑 soak 和 30 天观察日历时间。为隔离上游和安全风险，按 v1.2.0～v1.2.3
独立发布，每个切片独立完成迁移、兼容检查、e2e、回滚与 soak。

## 2. 入口门禁

v1.2 可以先完成 ADR 和上游 spike，但开始 schema/proto 实现前必须冻结一个可复现的
v1.1 基线：

- 清理当前工作树并打 v1.1 tag；README、实现纪要和实际版本一致；
- hypeman 所需改动进入不可变 commit/tag，release 构建不依赖 sibling checkout；
- `GOWORK=off make check` 通过；
- 2 compute、2 edge、3 Nomad/Consul server 的标准拓扑完成调度、节点失效、
  evacuate、VIP、leader handover、Redis 重投影和 PG 恢复验证；
- `docs/ga-observation-scorecard.md` 中相关项有结构化 PASS 证据，或有明确 waiver；
- 72h soak 无持续增长的 VM、netns、TAP、reservation、operation 和缓存残留。

入口门禁失败时只修复 v1.1，不把缺陷混入 v1.2 功能开发。每个切片开始实现前，
对应 ADR 必须从“提议”转为“已接受”，且其要求修订的旧 ADR 必须同步更新。

## 4. V1.2-A：Runtime capability discovery

**ADR：** [ADR-0023](adr/0023-runtime-capabilities-and-negotiation.md)。

### 工作项

1. `ServiceInfoResponse` 增加 `protocol_version`、稳定字符串 `feature_ids`、
   `snapshot_compatibility_key`；未知 feature 必须可忽略。
2. 首批 feature：`guest.exec.v1`、`guest.copy.v1`、`guest.logs.v1`、
   `secret.oneshot.v1`、`snapshot.memory.v1`、`snapshot.filesystem.v1`。
3. 能力分两类：启动正确性能力（如 one-shot secret、snapshot 格式）进入 placement
   硬过滤；按需运维能力（logs/exec/cp）在 action-time 检查目标 execution。
4. v1.2.1 对外承诺所有新建 machine 均支持 logs/exec/cp，因此滚动升级期间，
   不具备三项能力的旧节点先 drain，而不是用 deployment 字段隐式排除。
5. 节点能力随 nodemanager 同步进 PG；API 返回能力及支持节点数。
6. deployment 只保存平台推导的启动 `required_features`，客户端不能任意伪造内部能力。
7. scheduler 在资源打分前做启动能力硬过滤；不支持的节点不能靠降级绕过。
8. capability 与 agent/runtime/guest-agent 版本进入日志、事件和故障证据。

### 验收

- 新旧 agent 混跑时，要求 `secret.oneshot.v1` 的 deployment 只落到支持节点；
- 对旧 execution 调用 exec 返回明确 capability error；v1.2.1 升级门禁完成后新 machine
  全部具备 logs/exec/cp；
- 未知 feature 不破坏旧客户端或节点同步；
- agent 重启后一个同步周期内恢复能力投影；
- 无支持节点时返回可解释、可审计的 terminal reason。

## 5. V1.2-B：真正 one-shot secret 注入

**ADR：** [ADR-0024](adr/0024-one-shot-secret-delivery.md)。

### 契约

- PG 继续只保存信封加密值，deployment 继续只保存版本化引用；
- PG 持久化不含明文的 lease metadata，状态机为
  `ISSUED → CLAIMED → DELIVERED → ACKED | EXPIRED | REVOKED`，转换使用 CAS；
  明文只在控制面/agent 内存短暂存在，Redis 最多作为缓存；
- 每次 execution 创建短 TTL、单次消费的 secret delivery lease；claim、delivery
  和 ACK 均绑定 operation/request hash，结果可幂等重放；
- agent 通过 vsock guest channel 把 secret 写入 guest tmpfs（建议
  `/run/firepaas/secrets`，目录 `0700`、文件 `0400`）；
- guest init 在启动用户进程前消费 secret file；环境变量兼容由 guest init 在内存中
  构造，不写回 hypeman metadata/config disk；
- delivery 与 project/machine/execution/generation 绑定，旧 execution 和二次消费拒绝；
- ACK 后 agent 清除明文，PG 将 lease 置 ACKED；回收器处理 EXPIRED/REVOKED；
- guest 已写入但 ACK 丢失属于不确定结果：必须先 fence 并销毁旧 execution，再以新
  execution 和新 lease 重试，禁止向同一 execution 二次签发；
- **任何接收过 secret 的 execution 禁止 memory snapshot/checkpoint/fork**。
  tmpfs 仍属于 guest RAM，会进入 Firecracker 内存快照，canary 扫描不能证明无副本；
  只允许 filesystem-only checkpoint，并在冷启动后重新授权 secret。

### 上游工作

先在 hypeman 增加通用 guest secret-delivery API，并发布新 tag；firepaas 不把
hypeman build-only secret provider 私自复制成长期 fork。完成后将
`unsafe-persisted-env` 标记 deprecated，生产配置禁止启用。

### 验收

- canary secret 不出现在 PG 明文、Redis、operation、日志、agent state、hypeman
  metadata、config disk 和 snapshot；
- 错 project、旧 execution、过期和重复 lease 全部拒绝；
- 在下发前、ACK 前、ACK 后分别 crash agent，均不跨 execution 泄漏；
- secret app 默认可启动，不再需要不安全开关；
- leader handover 与 ACK 丢失交叉场景不二次交付；
- secret workload 的 memory snapshot/checkpoint/fork 明确拒绝；filesystem-only
  恢复、restart、rollout 后按 ADR 重新交付。

## 6. V1.2-C：Logs、Exec 与 Cp

**ADR：** [ADR-0025](adr/0025-guest-operations-channel.md)。

### 工作项

1. 实现现有 `StreamLogs` 和双向 `Exec` RPC；新增 CopyTo/CopyFrom 流式 RPC。
2. 数据路径固定为 `fpctl/API → mTLS agent → vsock guest agent`；CLI 不直连节点。
3. REST/streaming API：
   - `GET /v1/machines/{id}/logs?follow=&tail=`；
   - `POST /v1/machines/{id}/exec`；
   - `PUT|GET /v1/machines/{id}/files`。
4. `fpctl logs/exec/cp`；支持 argv、cwd、TTY、resize、stdin、signal、exit code。
5. 第一版 cp 只支持单个普通文件，不跟随 symlink；限制路径、大小、frame、速率、
   并发、空闲与总时长。
6. 所有会话绑定 project/machine/execution；execution 换代立即终止旧 session。
7. 审计只记录命令摘要、路径摘要、字节数、耗时和结果，不记录 stdin/stdout、env
   或文件正文。

### 验收

- logs tail/follow、stdout/stderr、exec TTY/signal/exit code 均可用；
- 100 MiB 边界文件双向 checksum 一致；越界和 symlink escape 被拒绝；
- 跨 project、read-only key、stale execution 被拒绝；
- 100 次建立/断开后 FD、goroutine、vsock session 回到基线；
- 客户端断开按 ADR 终止 exec，不留下后台会话。

## 7. V1.2-D：Wait API、TTL 与 Restart Policy

**ADR：** [ADR-0026](adr/0026-lifecycle-wait-ttl-and-restart.md)。

### Wait

- 提供 operation/machine/rollout 的有界 wait，HTTP 采用长轮询或 SSE；
- PG 状态是结果权威，进程内通知或 PG `LISTEN/NOTIFY` 只作加速，固定轮询兜底；
- 最大等待 5 分钟，客户端断开不取消底层 operation；
- wait 目标必须绑定对象 revision：`operation terminal`、`machine execution X ready`
  或 `rollout generation Y terminal`；generation/execution 被替换时返回 superseded，
  不能把旧代到达目标误判为成功；
- operation、machine 和 rollout 各自冻结 terminal state 集合；返回 reached、
  timed_out、superseded、terminal_reason 和当前 generation/execution。

### TTL

- PG 保存绝对 `expires_at`；`0/null` 表示关闭；
- 到期先从 route 摘除，再下发 fenced delete；
- controller 停机跨过到期点后，恢复时立即处理；
- 已删除/已过期 machine 不能通过更新 TTL 复活。

### Restart

- 控制面是 restart policy 唯一权威，不同时启用 hypeman 本地 restart controller；
- 支持 `NEVER`、`ON_FAILURE`、`ALWAYS`、`max_attempts`、固定 backoff 和
  stable window；
- restart 创建新 execution、递增 generation、重置 readiness、重新调度和重新获取
  one-shot secret；
- manual stop/delete、TTL expiry 不触发 restart；rollout 与 evacuate 有唯一 owner，
  不并发补副本；
- owner 决策表以 `rollout state × evacuate state × desired state × observed exit class`
  为输入：active rollout 负责 target replica；active evacuate 负责 source replacement；
  TTL/manual delete 禁止 restart；仅其余意外退出进入 restart；
- `ON_FAILURE` 的 exit class 来自 execution-bound agent exit report；agent/node 失联由
  R1～R8 故障重建处理，不消耗 restart attempts；rollout create retry 与 restart
  attempts 分开计数；计划性 evacuate 不消耗 attempts；
- attempts 按 logical machine 持久化，stable window 从新 execution READY 开始；
  pause 不重置，成功运行满窗口才清零；超限后 machine 进入 `RESTART_BLOCKED`，
  app controller 不补建该 ordinal，直到新 deployment 或管理员 reset；
- operation idempotency key 包含 machine、failed execution 和 attempt ordinal。

### 验收

- leader 切换、ACK 丢失、Redis 清空下不双重删除或双重重启；
- 最大次数后进入明确 blocked 终态，无 restart storm；
- `ON_FAILURE` 不重启正常退出，`ALWAYS` 重启正常退出；
- 100 个 wait 不持有长期 DB 事务且无 goroutine 泄漏。

## 8. V1.2-E：磁盘资源、动态配额与 API 限流

**ADR：** [ADR-0035](adr/0035-disk-quota-and-api-governance.md)。

### 工作项

1. `NodeCapacity/NodeUsage`、scheduler request、reservation Lua 和 agent admission
   增加 local disk requested/allocated/free-watermark 维度。
2. `projects` 增加 disk quota；管理员用 revision/ETag 更新 CPU、内存、磁盘、
   machine 并发和 runtime-session 并发额度。
3. 配额降低不驱逐已有 machine，只拒绝新的 create/restart/exec/cp。
4. API 限流按 `project + route_class`：read、mutation、runtime-stream；配置存 PG，
   内存短缓存，Redis 原子 token bucket。
5. Redis 故障：普通只读 fail-open；create、secret、exec/cp 等高成本或敏感操作
   fail-closed，并输出明确指标。
6. 本版网络带宽与 IOPS 先进入 ServiceInfo/metrics，不作为承诺配额；待数据充分后
   再进入调度硬过滤。

### 验收

- 100 并发 create 不能突破 CPU、内存、磁盘任一项目/节点上限；
- 控制面数据滞后时 agent 磁盘硬准入仍能拦截；
- project A 耗尽不影响 project B；
- 配额/限流在声明缓存窗口内生效且不需重启；
- Redis 故障行为与风险分级一致，reservation 重建不永久假满。

## 9. V1.2-F：用户事件、指标和引用感知 GC

### 用户可观测

- 新建 append-only `user_events`，与内部 `scheduler_events` 分离；
- 事件覆盖 machine、rollout、restart、expiry、secret delivery、quota/rate-limit；
- 所有租户事件必须有 project attribution，不得包含 secret、command env、文件正文；
- `/v1/events` 支持 project/app/machine/type/time/cursor；默认保留 7 天，最大 30 天；
- Prometheus 增加 session、字节、restart、expiry、disk 和拒绝指标；禁止 path、
  command、execution ID 等无界 label。

### GC

- 区分 converted image、OCI blob、snapshot、operation/event retention；
- image roots 合并 PG active/rollback/in-flight deployment 与 agent live instance；
- prefetch 中、最近创建、无法解析但被引用的 digest 不可删除；
- 高水位触发、低水位停止，先 dry-run 一个发布周期再启用删除；
- GC 永远不删除 PG desired state、运行 VM 或 slot。

### 验收

- 租户只能查看自己的事件；retention 后分页结果正确；
- dry-run 不包含 active、rollback、in-flight root；
- 删除冷缓存后可重新 pull 并启动；
- 72h 中事件表、ledger 和缓存占用有界，无 GC/prefetch 抖动。

## 10. 明确非目标

- E2B envd 的 process reattach、filesystem watch、在线 agent fd handover；
- exec 断线续传、后台持久 session；目录递归 cp、xattr/ACL 完整保真；
- Loki/ClickHouse 和历史日志搜索；
- app 级 edge 并发、跨 edge 全局 inflight；
- node-local volume、有状态 SLA、checkpoint/fork；
- 域名/SNI egress、credential broker；
- Dockerfile build、Web console、计费引擎；
- balloon、UFFD、GPU、多 hypervisor、多集群；
- mesh、6PN、WireGuard、内部 DNS（ADR-0016 不变）。

## 11. 发布切片与依赖

```text
v1.2.0  A capabilities + B one-shot secret
v1.2.1  C logs/exec/cp
v1.2.2  D wait/TTL/restart
v1.2.3  E disk/quota/rate-limit + F events/metrics/GC
```

- A 是 B 的前置；C 只依赖 A 的 action-time capability，可与 B 的上游开发并行，
  但 v1.2.1 发布不依赖 secret workload；
- D 的普通生命周期可与 C 并行，涉及 secret 的 restart 验收依赖 B；
- E 的 schema/admission 与 C 独立，可提前实现；F 依赖 C～E 的事件类型稳定；
- 每个切片都形成 migration/proto/API/agent/controller/CLI/metrics/e2e 的纵向闭环，
  并有独立回滚和至少 24h soak；v1.2 总版本再执行 72h soak。

## 12. 发布验收

- `make check`、`make check-lab`、`make sim` 全绿；
- `e2e-m1`～`e2e-m5`、`e2e-v11` 全绿；
- 新增 `scripts/lab/e2e-v12.sh` 覆盖 A～F；
- 多节点覆盖 capability 混跑、restart 换节点、leader handover、GC/prefetch；
- 安全负路径覆盖 secret canary、旧 execution、跨 project、路径逃逸、超大 cp、
  限流 Redis 故障；
- 标准拓扑 72h soak 无 secret 落盘、session/FD/vsock 泄漏、restart storm 和磁盘
  无界增长；
- release 使用已发布 hypeman tag，`GOWORK=off` 可复现构建。

## 13. 风险与裁剪顺序

| 风险 | 决策 |
|---|---|
| guest agent 无法在用户进程前完成安全 secret ACK | 阻断 B；不得恢复默认明文 env；可先限定受支持基础镜像 |
| secret 被 memory snapshot 捕获 | 接收过 secret 的 execution 禁止 memory snapshot/fork；只允许 filesystem-only 冷恢复 |
| 双向流拖期 | 先裁 TTY resize，再裁 logs cursor；保留非交互 exec 和单文件 cp |
| TTL/restart 与 rollout 竞争 | 所有动作写 PG operation；组合决策表指定唯一 owner |
| disk accounting 偏差 | requested 用于调度，agent free-space 水位最终硬准入 |
| GC 误删 | dry-run、最小年龄、合并 PG+agent roots；自动删除可降级为告警 |
| PG 事件增长 | 短 retention 和批量删除；达到实测阈值后才评估 ClickHouse |

超期时按顺序裁剪：TTY resize → logs cursor → 大文件 cp → 事件高级过滤 → GC
自动删除 → 磁盘打分（保留硬准入）。不得裁剪 one-shot secret、execution fencing、
原子配额和跨项目负测试。
